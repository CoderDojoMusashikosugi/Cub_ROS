# 2D画像からGodotワールドを生成する計画

ワールド生成用に編集したPGMから、平らな床と高さ0.5 mの壁を生成する。開始前にホストが文字の一覧からワールドを選び、クライアントはホストと同じワールドを読み込む。開始位置はプリセットまたは起動引数で指定する。将来は同じワールド選択・通信・移動の仕組みに、3Dメッシュ用ローダーを追加できる構成にする。

ワールドは実際の周囲の環境に相当し、ROSのナビゲーション地図とは独立して管理する。両者の障害物配置が異なることを許容し、ワールド変更を理由としたROS地図の自動切替・一致確認・Nav2再起動は行わない。正解オドメトリ・TF・簡易LiDAR・commanderの経路を利用する。

## 方針

- 2D画像を入力とし、黒い領域を高さ0.5 mの壁、白・灰色の領域を空きの床として扱う。
- 地図の膨張・平滑化・穴埋め・ノイズ除去・切り出しは行わない。セルの結合は形状を変えない軽量化として扱う。
- ワールド用PGMとROSで指定するナビゲーション地図は別のデータとして扱う。
- ワールド変更はシミュレーター内で完結する。ROS側への地図切替要求、地図一致を条件とした開始制限は設けない。
- ワールド選択画面は文字だけとし、プレビュー画像・サムネイルは用意しない。
- ホスト・クライアントとも、自身の操作対象の開始位置を起動引数で指定できるようにする。
- 共通ワールド定義と種類別ローダーを分け、将来の3Dメッシュ対応で操作・通信・ROS接続を作り直さない。

## 1. 対象データの構成

入力画像の例: `docker/home/maps/gnss2026/mid360/1017_02/map_navigation.pgm`。縮尺・原点は同じディレクトリの`map.yaml`を引き継ぐ。

| 項目 | 内容 |
| --- | --- |
| 画像 | P5 / 3580 × 2122 / 8 bit、約7.3 MiB |
| 解像度 | 0.2 m/cell |
| 地図原点 | ROS座標で `[-92.4275, -100.706, 0]`。3番目はyaw |
| 全体寸法 | 716 × 424.4 m |
| 黒・占有 | 値0、65,640セル |
| 白・空き | 値254、7,530,733セル |
| 灰色（ワールドでは空き） | 値205、387セル |
| PNGへのロスレス変換 | 同じ全画素を保ったグレースケールPNG（50,992 bytes） |
| 既定開始地点（`start_a`） | ピクセル `(u=773, v=1467)`、画像上で左向き（`-u`方向＝ROS `-X`、`yaw = 180°`、ROS `map` 座標 `(62.2725, 30.194, 0.0)`） |

`map.yaml`の`image`は**`map.pgm`**を指しているため、ワールド生成では`map_navigation.pgm`を画像として明示指定し、YAMLからは縮尺・原点などの生成用情報を取得する。ROSのナビゲーション地図を変更したり、このPGMへ参照を差し替えたりする必要はない。

入力画像の約99.1%は白で、灰色も含めてワールド内の空き領域として扱う。道路の内外を推測せず、元画像全体から床と黒い壁を生成する。

Godotのワールド・参加時のワールド識別・開始位置・落下後の復帰位置はすべてワールド定義から取得する。

## 2. 初期版の仕様

| 項目 | 推奨 |
| --- | --- |
| 地形 | 全画像範囲の平らな床。占有セルを高さ0.5 mに押し出す |
| 壁の判定 | 黒（画素値0）だけを壁とし、白・灰色は空きにする。ROS地図の占有判定の閾値は流用しない |
| 灰色領域 | 白と同じ空きの床。壁を作らず、必要な配置余裕があれば開始位置にも選べる。ROS側の未知領域設定は変更しない |
| 形状加工 | 占有セルの面積を保つ。膨張・平滑化・小障害物除去は行わない |
| 床の外 | 画像外には床を延長しない。範囲外・落下はワールドの安全な開始地点へ復帰 |
| LiDAR | 床は検出対象外。生成した壁は移動用・LiDAR用の両方の対象 |
| ワールド選択 | ホストが開始前に選ぶ。接続中の変更は行わない |
| 選択画面 | ワールド名・開始地点名などを文字で表示。画像は使わない |
| クライアント | 参加先ホストのワールドを自動選択。初期版は全端末に同じデータを事前配布 |
| 開始位置 | 既定プリセットに加え、ホスト・クライアントの起動引数で自身の開始位置を指定可能 |
| ROS地図選択 | 従来どおりROS側で`map:=<yaml>`を指定。ワールドの選択・変更とは連動させない |
| ナビゲーション目標 | ROS側で管理。ワールド選択処理は地図やウェイポイントを差し替えない |

高さ0.5 mの壁は現在の乗り越え上限0.24 mより高い。床を0 mとしたとき、既存LiDARの高さ0.2492 mに壁がかかるため、センサー位置の変更は不要。

## 3. ワールドデータの管理

初期配置案は`simulator/worlds/<world_id>/`とし、Godot用のワールド一式を配置する。ROSにこのフォルダーを読ませるためのDockerマウントやROSパッケージへのコピーは不要。別PCではGodot側へフォルダー単位で配布する。OSごとの絶対パスは通信データやワールド定義に含めない。

```text
simulator/worlds/gnss2026_mid360_1017_02/
  world.json             # 共通情報と、2D画像用の生成条件・参照
  source.png             # 元PGMの全画素をロスレス保存。生成・検証用でUIには表示しない
  wall_chunks.json       # セル境界に沿う結合矩形。再生成可能な形状キャッシュ
```

変換ツールの入力はPGMと縮尺・原点の設定。YAMLからの設定取り込みも用意し、今回のようにYAMLと異なる画像を明示指定できるようにする。取り込んだ数値は`world.json`の種類別設定へ保存する。Nav2用YAMLや選択画面用の画像は生成しない。通常のプレイでは事前生成済みデータを読み、PGM/YAMLの解析やPythonの実行は不要にする。必要なデータをGodotのエクスポート対象へ含める。

PGMからPNGへの保存形式変更では元の全画素を保つ。値205を壁にしないのはワールド生成時の解釈であり、元画像の書き換えや画像の平滑化は行わない。

`docker/home/maps`はGit管理外なので、元データの存在を他PCで前提にしない。配布・Git管理の単位は生成したワールドフォルダーとする。元ファイルの参照名・SHA-256・変換条件を記録し、再生成可能にする。登録済みワールドの更新は明示的な再生成で反映する。

| 情報 | 管理方針 |
| --- | --- |
| `schema_version` / `kind` | 共通定義の版と種類。今回は`occupancy_extrusion`、将来の`mesh`用ローダーを追加できる構成 |
| `world_id` / `display_name` | 安定した機械用IDと、変更可能な表示名を分ける |
| 共通情報 | ワールド範囲・開始地点・参照アセット・配置の情報を扱う。PNGや解像度は全種類の必須項目にしない |
| 種類別の入力 | 2D画像では画像・解像度・原点・壁判定・灰色の扱い。3Dではメッシュ参照・縮尺・軸の変換などを扱えるよう分離 |
| 生成条件 | 2D用の壁高・床高・形状生成の版・チャンクサイズなどは種類別の設定にする |
| `world_hash` | アセットと読み込み・生成条件を識別し、Godotの参加者同士だけで照合する。ROSの地図との比較には使わない |
| 開始地点 | ロボット用とクライアント用3地点の既定値を共通座標で保持。3D位置とyawを扱い、実際の採用位置はホストが配信 |
| 実行時情報 | 操作対象、現在位置、カメラ、選択した開始地点などはセッション側に保持 |

現在の試験ワールド`cub_playground_v1`も同じ選択・識別の仕組みに登録する。経路や歩行者の自動行動を保存するシナリオ機能は、必要になった段階で追加する。

### 3Dメッシュ用ローダーを追加できる境界

`WorldDefinition`相当の定義を`kind`ごとのローダーへ渡し、同じ契約の`WorldInstance`相当のノードを作る。初期版で実装するのは2D画像と既存試験ワールドであり、3Dメッシュの取り込み自体は後から追加する。

共通側が利用するのは「読み込み完了」「3Dのワールド範囲」「開始地点の解決・配置可否」「移動用地形」「LiDAR用形状」とする。カメラ・アクター・通信は画像のセルや解像度を直接参照しない。

2Dローダーは床と押し出した壁を作る。将来の3Dローダーは表示用メッシュ・静的な移動用形状・床を除いたLiDAR用形状を用意し、同じ衝突レイヤーの契約へ合わせる。上方向・縮尺・配置を共通座標へ揃える処理と、地面の高さを求める処理はローダー側に置く。3DメッシュからNav2地図を自動生成する処理は、このワールド読み込み機能には含めない。

## 4. 選択操作と開始位置

開始前のホスト画面に、文字だけの「ワールド一覧」「開始地点一覧」を追加する。必要な種類名・読み込み状態・エラーも文字で表示し、プレビュー画像・サムネイル・画像クリックによる位置指定は用意しない。データの読み込み・検証後にHostを有効にする。プレイ中のUIは現在の下部1行を維持し、ワールド名を短く表示する。

初期版はワールドごとの開始地点プリセットを用意する。ワールド全体が広いため、空き領域の自動選択だけに依存せず、登録時に試走用の既定地点を用意する。起動引数ではプリセット名に加え、任意の開始座標も指定できるようにする。

開始地点は、ワールド範囲内であることに加え、周囲に移動用カプセルを置ける余裕があることを検証する。2D画像では白・灰色を空きとして扱い、空きの1セルだけでは配置可能とみなさない。各クライアントが引数で指定した位置もホストが検証・採用して配信する。アクター同士の衝突・配置競合の解決は追加しない。

クライアントのJoin画面ではワールドを選ばない。ホストから受け取ったワールドID・ハッシュに対応するデータを読み込み、完了してからアクターを生成する。不足・版違いの場合は、ワールド名と必要なデータを表示して参加を中断する。

ワールドの起動引数案はホストの`--world gnss2026_mid360_1017_02`。クライアントはワールドを指定せず、参加先に追従する。未指定のホストは既存試験ワールドを使い、ロビー操作と起動引数で同じ設定を利用する。

開始位置の引数案は次のとおり。ホスト・クライアントのどちらにも使える。

| 引数 | 内容 |
| --- | --- |
| `--spawn start_a` | 参加するワールドの開始地点プリセット名 |
| `--spawn-x X --spawn-y Y` | 自身の操作対象の開始位置。ROSと同じ共通座標でm単位。X・Yは両方指定 |
| `--spawn-z Z` | 高さをm単位で明示指定。座標指定モードの任意項目 |
| `--spawn-yaw-deg ANGLE` | 向きを度単位で指定。ROSの+X方向を0度、左旋回を正。座標指定モードで省略した場合は0度 |

```text
# ホストの開始位置・向きを座標で指定（座標値は記述例）
-- --host --world gnss2026_mid360_1017_02 --spawn-x 0 --spawn-y 0 --spawn-yaw-deg 90

# クライアントの開始位置も、ホストが選んだワールドの共通座標で指定
-- --join 127.0.0.1 --actor pedestrian --spawn-x 2 --spawn-y 0

# プリセットで指定
-- --host --world gnss2026_mid360_1017_02 --spawn start_a
```

プリセット指定と座標指定は同時に使わない。Z・向きだけの指定、X/Yの片方だけの指定、非有限値、範囲外・壁内部など配置不可の指定は理由を文字で表示し、別位置へ黙って置き換えない。指定がなければワールドの既定地点を使う。有効な起動引数は画面の既定選択より優先する。

Z省略時はローダーへ地面の高さを問い合わせ、接地可能な位置へ配置する。今回の2Dワールドでは床0 mと既定の配置余裕を使う。将来の3Dローダーでは地形の高さを使い、複数の高さの面が重なるなど自動決定できない場合にはZを明示指定できる設計にする。クライアントの要求位置は参加手順でホストへ送り、検証後の確定位置を全参加者へ配信する。

全体表示は716 mのワールドに対応するよう、カメラの遠方クリップとズーム上限を種類に依存しないワールド範囲から調整し、初期視点は操作対象の確定開始位置へ合わせる。`3`キーの真上2D地図カメラはPGM画像の向き（画面上＝画像上`-v`＝ROS `+Y`＝Godot `-X`、画面右＝画像右`+u`＝ROS `+X`＝Godot `-Z`）に合わせる。

## 5. 壁の生成と軽量化

黒セルごとにNodeやStaticBodyを作る方式では、壁だけで65,640個になる。セルを連続矩形にまとめ、さらに空間ごとのチャンク単位に描画メッシュ・静的衝突形状をまとめる方式とする。

横方向の連続セルは22,587区間、隣接行の同じ区間をまとめるだけで13,909矩形になる。64 × 64セル（12.8 m四方）の区切りでは、占有セルのあるチャンクは309個（チャンク内結合矩形14,355個）となる。

64 × 64セル単位で、矩形結合後の壁メッシュと静的衝突形状をチャンクごとに構築する。壁同士の内側の境界面は省きつつ占有範囲は変えない。移動・LiDARは静的な衝突形状を利用し、カプセルと壁の衝突、細い壁、高速移動、チャンク境界の滑走を保つ。影なし・FPS上限（45/30 FPS）を維持する。

描画の代案は矩形のMultiMesh化。ただしMultiMeshは描画の集約であり、物理衝突の集約は別途必要。1つの巨大なMultiMeshには個々の壁の視錐台カリングがないため、この場合もチャンク分割する。[GodotのMultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)、[静的な三角形衝突形状](https://docs.godotengine.org/en/stable/classes/class_concavepolygonshape3d.html)

## 6. 座標とROSナビゲーションの独立性

PGM左上を画像の`(u=0, v=0)`とする。解像度`r`・高さ`H`のとき、セル中心の地図ローカル座標は`((u+0.5)r, (H-v-0.5)r)`。YAMLの原点yawで回転してから原点位置を加え、ROSのmap座標へ変換する。

Godotへの変換は`Godot(x, y, z) = ROS(-y, z, -x)`を使う。セル中心とセルの外周を区別し、壁はセルの外周に合わせて立てる。開始位置を基準に地図の原点を移動しない。`map -> odom`の恒等変換と真値オドメトリを維持する。

2D画像では黒（画素値0）を壁とし、それ以外の白・灰色を空きへ分類する。対象は8 bitグレースケール画像とし、非対応形式は変換時にエラーを出す。回転した原点、上下反転、端のセル、異なる濃淡の灰色が空きになることを小さな試験画像で確認する。

ROSは`navigation.launch.py simulation:=godot map:=<ナビゲーション用YAML>`で起動する。ワールドのIDをROSの起動引数へ追加する必要はなく、ワールドとナビゲーション地図の同一性も要求しない。シミュレーターは環境と真値位置・センサー情報を提供し、ROS側は利用者が指定した地図でナビゲーションする。

`nav_map_hash`や`/sim/world_info`によるROSとの照合、ワールド選択からのLoadMap要求・地図差し替え・Nav2再起動・目標キャンセルは含めない。`world_hash`はGodot参加者が同じ環境を読み込んでいるかだけを確認する。

座標の単位・軸・ワールドの配置は共通の約束に従わせる。ROS上でどのナビゲーション地図を選び、どの位置関係で試すかは利用者が設定する。環境に壁があるのに地図にはない、といった差異も検証対象にできる。必要なら利用者がROS側で地図・目標・ウェイポイントを変更するが、ワールド選択処理からは行わない。

## 7. オンライン参加と切替

ホストが選んだワールド情報による参加手順は次のとおり。

1. ホストはワールドの生成・衝突形状の準備を完了してから参加を受け付ける。
2. クライアントが接続し、ホストがID・版・ハッシュ・必要な生成条件を通知する。
3. クライアントが該当ワールドを読み込み、衝突形状の準備後にReadyを返す。
4. Ready確認後にホストがアクターを生成し、現在位置を配信する。途中参加も同じ手順。

ワールド読み込みとネットワーク接続のタイムアウトを区別し、読み込み中の状態を表示する。読み込み前の床で移動したり、別ワールドへ位置が配信されたりしないようにする。

ワールドの切替は、退出してから開始前画面で選び直す。ホスト退出時は全クライアントのセッションも終了する。旧ワールドのアクター・補間履歴・シミュレーター内の速度キャッシュを消し、再開後は新しく受信した指令を使用する。ROS接続の終了・再開はセッション処理に従う。ROSの地図、実行中のナビゲーション目標、ノードの起動状態はワールド選択処理から変更しない。

## 8. 選択肢と方針

| 判断点 | 採用方針 | 別案・拡張時の扱い |
| --- | --- | --- |
| ワールド登録 | 事前変換してGodot用フォルダーへ配置 | 任意フォルダーを登録する操作を追加する場合は、参照先の保存と不足ファイルの検証が必要 |
| クライアントのデータ | 同じワールドを事前配布し、選択は自動 | 不足データの転送・キャッシュは後で追加可能。将来の3Dアセットも扱える単位で設計する |
| 開始位置 | 文字のプリセット一覧と起動引数 | 任意位置は引数で指定し、入力検証・ホスト側の採用処理を共通化する |
| 壁の描画 | 区画ごとの結合メッシュ | MultiMesh化する場合も物理形状を別途まとめ、4ウインドウで測定する |
| 再生中の切替 | 退出して選び直す | 接続維持には全員の読み込み待ちとアクター状態の一括切替が必要。ROS地図はどちらの方式でも変更しない |

ROS地図との独立、文字だけの選択画面、灰色の空き扱い、形状加工なしは確定事項とする。

## 9. 実装工程と確認項目

| 工程 | 実装内容 | 完了条件 |
| --- | --- | --- |
| 1. ワールド変換 | PGM・生成設定の読込、共通定義・結合矩形の生成、開始地点設定 | 黒の壁領域が元画像と一致し、白・灰色が空きになる。画像加工がなく、同じ入力から同じ内容が生成される |
| 2. 単独ワールド | 種類別ローダーと共通契約、床・0.5 m壁、試験ワールド、カメラ範囲、復帰位置 | 開始地点から手動で走行し、壁に衝突する。LiDARは壁を検出し床を検出しない。共通側が画像固有の値に依存しない |
| 3. 選択とオンライン | 文字の一覧、プリセット・座標引数、ワールド照合、読み込みReady | ホスト＋3クライアント、途中参加、引数指定位置の配信・不正位置の拒否、同名別版・切断を確認 |
| 4. ROS経路との確認 | Nav2起動・地図指定と、真値姿勢・scanによる走行 | ROS地図と環境の差異があっても一致照合で開始を拒否しない。ワールド変更で地図切替・目標取消・再起動要求を送らず、壁のscan・回避を確認 |
| 5. 軽量性 | 実データの4ウインドウ同時起動、読み込み時間・メモリ・フレーム時間・LiDAR処理時間の測定 | 45/30 FPS上限と60 Hz移動に対して負荷を確認。問題があればチャンクサイズ・形状生成を調整して再測定 |

自動検証は、小画像での座標・灰色の空き扱い・壁寸法・形状結合、プリセットとX/Y/Z/yaw引数の解決・競合・省略・配置検証、複数プロセスでのワールド合意を中心にする。実データでは離れた複数地点も確認し、反転・原点ずれ・遠方描画の欠落を見つける。高速で薄い壁を通過しないこと、チャンク境界に引っかからないことも確認する。

性能は実データで測定して判断する。ピクセル数や形状数の集計だけで4ウインドウ動作を保証しない。ROSコマンドとビルドはプロジェクトのルールどおり`docker/run_in_container.sh`経由で実行する。
